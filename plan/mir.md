# MIR Design v3: The Pragmatic Memory Model

## Core Philosophy

1. **MIR is Imperative:** All data lives in `Slots` (stack memory). Instructions are simple transactions on these slots.
2. **Type-Driven:** Slots always carry full type information. References are opaque handles, not integers.
3. **Versioning is a Side-Table:** We do not bake SSA into the IR instructions. We compute a **MemorySSA** graph on demand.
4. **Two-Track Optimization:**

* **Track A (Virtual Slots):** Promoted to registers (virtual) via `mem2reg`.
* **Track B (Physical Slots):** Kept in memory (address taken), optimized via MemorySSA.

## Part 1: The Core Data Model

### 1.1 The Slot (Stack Allocation)

The atomic unit of storage. Everything—user variables, temps, and arguments—is a slot.

```cpp
using SlotId = uint32_t;

struct Slot {
    TypeId type;
    std::string debug_name; // e.g., "x", "_temp_0"
    
    // Properties determined by frontend/scan
    struct Flags {
        bool is_temp : 1;       // Generated by compiler?
        bool is_immutable : 1;  // declared with 'let' vs 'let mut'
        bool address_taken : 1; // Was '&x' ever created?
    } flags;
};

```

### 1.2 The Projection (The Drill)

To access data inside a Slot, we apply Projections. This enforces the rule that **References are Paths**, not just values.

```cpp
struct Projection {
    enum class Tag { 
        Deref,      // *ptr
        Field,      // struct.field_index
        Index,      // array[index_slot]
        Downcast    // enum as Variant
    } tag;
    
    // Payload for Field/Index/Downcast
    std::variant<std::monostate, uint32_t, SlotId> data;
    
    static Projection Deref() { return {Tag::Deref, {}}; }
    static Projection Field(uint32_t i) { return {Tag::Field, i}; }
};

```

### 1.3 The Place (L-Value)

A `Place` describes a **location** in memory. It is a path starting from a root Slot.

```cpp
struct Place {
    SlotId local;                 // The Root
    std::vector<Projection> path; // The Path
    
    // Helpers
    Place deref() const {
        Place p = *this;
        p.path.push_back(Projection::Deref());
        return p;
    }
};

```

### 1.4 The Operand (Leaf Data)

Data ready to be used. Either a constant or a value read from a Place.

```cpp
struct Operand {
    enum class Tag { Constant, Copy, Move } tag;
    
    // If Constant: holds raw bytes/int
    // If Copy/Move: holds the Source Place to read from
    std::variant<uint64_t, Place> value; 
};

```

## Part 2: The Instruction Set

We use `RValue` to encapsulate "Value Generation" logic, keeping the `Statement` struct clean.

### 2.1 R-Values (Value Generators)

These are helper structures that describe *how* a value is computed. They do not have a `dest` because they are just the "Right-Hand Side" of an assignment.

```cpp
struct RValue {
    enum class Tag {
        // 1. Trivial Read
        Use,            // Just read an operand (copy/move)
        
        // 2. Reference Creation (The "AddressOf" Op)
        Ref,            // &place
        RefMut,         // &mut place
        
        // 3. Math & Logic
        BinaryOp,       // a + b
        UnaryOp,        // -a
        
        // 4. Aggregates
        Aggregate,      // [a, b, c] or Point { x, y }
        
        // 5. Enum logic
        Discriminant,   // Get enum variant index
    } tag;

    // Payload
    struct Data {
        std::optional<BinaryOp> op;     // For BinaryOp
        std::vector<Operand> args;      // Inputs (Used by Binary, Aggregate)
        std::optional<Place> ref_target;// For Ref/RefMut (The target we borrow)
    };
    Data data;
};

```

### 2.2 Statements (The Imperative Unit)

The `Statement` is the actual instruction in the block. It creates the side effects.

```cpp
// 1. Assignment: dest = RValue
struct Assign {
    Place dest;   // <-- The ONLY place a value is written
    RValue rval;  // <-- The computation
};

// 2. Function Call: dest = func(args)
struct Call {
    Place dest;
    Operand func;
    std::vector<Operand> args;
    std::optional<BasicBlockId> target; // Where to go next
    std::optional<BasicBlockId> unwind; // If panic occurs
};

// 3. Storage Markers (Lifetime)
struct StorageDead {
    SlotId slot; // "Slot is now garbage"
};

// The Top-Level Statement Variant
using StatementKind = std::variant<Assign, Call, StorageDead, Nop>;

struct Statement {
    StatementKind kind;
    SourceInfo source_info; // Debug info (Line #)
};

```

## Part 3: MemorySSA (The Versioning System)

We do not just version variables; we version **Memory States**.

### 3.1 The Three Access Types

| Type | Trigger | Meaning | Versioning Action |
| --- | --- | --- | --- |
| **Def** | `Assign(dest)` | **Must-Write.** Old value is gone. | `dest.2 = Def(dest.1)` |
| **Use** | `RValue::Use(src)` | **Read.** No change to memory. | `Read(src.2)` |
| **Clobber** | `Call()` | **May-Write.** We aren't sure if `x` changed. | `x.3 = Clobber(x.2)` |

### 3.2 The Side Table Structure

```cpp
struct MemorySSA {
    // 1. Version Map: "Statement S defines Version V"
    DenseMap<StatementIndex, VersionID> defs;
    
    // 2. Use Map: "Statement S reads Version V"
    DenseMap<StatementIndex, std::vector<VersionID>> uses;
    
    // 3. Block-Level Phis
    DenseMap<BasicBlock*, DenseMap<SlotId, VersionID>> block_phis;
};

```

## Part 4: Analyzing References (The "State Machine")

Because you are compiling a Rust-like language, you track **Slot States**.

### 4.1 The 3 States of a Slot

| State | Condition | Capabilities | Optimization Implication |
| --- | --- | --- | --- |
| **Active** | No live references. | Read ✅ Write ✅ | **Promotable.** Can be `mem2reg`'d. |
| **Frozen** | `&T` exists. | Read ✅ Write ❌ | **Constant.** Loads are redundant. |
| **Locked** | `&mut T` exists. | Read ❌ Write ❌ | **Ghost.** Access only via ptr. `x` is dead. |

### 4.2 The Analysis Algorithm (The "Walker")

To build MemorySSA, we walk the CFG. We maintain a **Shadow Stack** of active borrows.

**Scenario: `let r = &mut x; *r = 20;**`

1. **`Assign { dest: r, rval: RefMut(x) }`**

* Mark `x` as **Locked**.
* Record `r` as the **KeyOwner** of `x`.

1. **`Assign { dest: *r, rval: 20 }`**

* Is `r` the KeyOwner of `x`? Yes.
* **Action:** Create new version `x.2 = Def(x.1)` (attributed to the store via `r`).

1. **`Assign { dest: y, rval: Use(x) }` (Error Case)**

* Check `x` state. **Locked.**
* **Result:** Compile Error (Borrow Checker) OR Optimization (Forwarding from `*r`).

1. **`StorageDead(r)`**

* `r` dies.
* **Commit:** `x` transitions back to **Active**.

## Part 5: The Optimization Pipeline

### Track A: `mem2reg` (The Ideal Path)

**Target:** "Virtual" Slots.

* **Criteria:** `address_taken == false` (never the target of `Ref/RefMut`).

**Action:**

1. **Promote:** Treat `SlotId` as a Virtual Register ID.
2. **Rewrite:** `Assign` becomes a register move.
3. **Phi:** Insert standard SSA Phis.

### Track B: Memory Optimization (The Fallback)

**Target:** "Physical" Slots (Escaped, Aliased).

**Opt 1: Redundant Load Elimination (RLE)**

* **Pattern:** `Assign(x, 10)` ... `Assign(y, Use(x))`
* **Check:** MemorySSA says `Use(x)` reads the version defined by `Assign(x, 10)`.
* **Action:** Replace `Use(x)` with `Constant(10)`.

**Opt 2: Dead Store Elimination (DSE)**

* **Pattern:** `Assign(x, 10)` ... `Assign(x, 20)`
* **Check:** Does anyone read the version from `Assign(x, 10)`?
* **Analysis:** If `Uses` list is empty, delete the first assignment.

**Opt 3: Reference Propagation**

* **Pattern:** `let r = &mut x; *r = 10; y = *r;`
* **Analysis:** `r` is the **KeyOwner**.
* **Action:** Treat `*r` exactly like `x`. `y` becomes `10`.

## Part 6: Lowering to LIR

When optimizations are done, we lower to LIR (Low-Level IR).

1. **Virtual Slots:** Lower to Virtual Registers. Register Allocator maps them to physical registers (`RAX`, `RBX`).
2. **Physical Slots:** Lower to Stack Offsets (`RBP - 8`).
3. **Projections:**

* `Place(x, [Field(1)])` → `LEA RAX, [RBP - 8 + offset]`
* `Place(r, [Deref])` → `MOV RAX, [r]; MOV [RAX], ...`
